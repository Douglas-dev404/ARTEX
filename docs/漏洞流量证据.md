# Evidências de múltiplos tráfegos por vulnerabilidade

O "Tráfego associado" nos detalhes da vulnerabilidade permite seleção múltipla entre páginas, finalidade e descrição, ordenação e desvinculação. A página de Tráfego também permite selecionar vários registros e associá-los de uma vez a uma vulnerabilidade existente. As evidências de vulnerabilidades herdadas pela tarefa são somente leitura; para alterá-las é preciso entrar na tarefa de origem.

A opção "Agent vincula tráfego automaticamente" nas configurações do sistema vem desativada por padrão; a leitura e a alteração são feitas pela interface `/api/settings`, campo `agent_traffic_binding`. Ativá-la aumenta o consumo de Tokens com a consulta de requisições/respostas, chamadas de ferramentas e prompts; a próxima rodada do Agent usa a nova configuração. Desativada, os parâmetros de vinculação automática e a ferramenta de vinculação posterior ficam ocultos, a orientação de vinculação automática não é injetada, e novas vinculações automáticas enviadas por sessões já em execução são rejeitadas. A vinculação manual, a captura de tráfego, a leitura de evidências já salvas e a exportação não são afetadas.

Com a opção ativada, o fluxo padrão é "achado registrado → Agent de relatório disparado automaticamente → conferir e vincular tráfego → escrever o relatório com a versão mais recente das evidências". Quem reporta mantém em `evidence` o comando de verificação, a saída principal, os IDs de tráfego reais já existentes e suas finalidades; o Agent de relatório, com base nos detalhes da vulnerabilidade e no registro de execução, confere com `traffic_search` / `traffic_get`, chama `bind_finding_traffic` e depois lê a `version` mais recente para salvar o relatório. Com a opção desativada, o Agent de relatório não recebe as ferramentas extras de busca/leitura de tráfego bruto nem vincula automaticamente; ainda assim consegue ler os snapshots vinculados manualmente e gerar o relatório.

Compatível com chamadores existentes: `traffic_refs` / `evidence_hint_id` de `report_finding` ainda podem vincular de forma explícita e imediata. A vinculação é opcional: para vulnerabilidades não HTTP, como TCP, ou quando o registro exato não foi coletado ou não é encontrado, omitir a referência não impede reportar nem redigir o relatório; mantenha outras evidências verificáveis, como saída de comandos e logs, e recomenda-se explicar o motivo de não haver vínculo, sem criar campo obrigatório novo. Os IDs enviados precisam ser todos válidos e o conteúdo completo. Se qualquer um falhar, toda a operação de vinculação é revertida; se a vinculação explícita junto com o reporte falhar, o reporte inteiro é revertido. Anexar repetidamente o mesmo snapshot não aumenta os vínculos nem sobrescreve a descrição.

## Numeração do Agent e versão do relatório

`report_finding` ganhou parâmetros opcionais; a ordem do array é a ordem inicial das evidências:

```json
{
  "traffic_refs": [
    {"traffic_id": "ID real do tráfego", "role": "baseline", "note": "requisição de conta normal"},
    {"traffic_id": "outro ID real do tráfego", "role": "proof", "note": "requisição de reprodução"}
  ]
}
```

As finalidades são `baseline` (controle normal), `proof` (prova da vulnerabilidade), `verification` (verificação complementar) e `supporting` (evidência auxiliar, padrão). Confira primeiro os registros reais com `traffic_search` / `traffic_get`; domínio e horário servem apenas para triagem de candidatos e não permitem presumir a que tarefa pertencem.

O prompt tem como referência a [orientação de reporte de vulnerabilidades do CyberStrikeAI](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go), combinada com a convenção de vinculação opcional deste projeto, sem introduzir validação que exija informar o motivo de não haver pacote. Não é permitido adivinhar IDs, nem sondar repetidamente apenas para obter o pacote.

A primeira linha do retorno continua sendo `finding recorded: <ID do nó de exploração>`; em seguida, um JSON fornece o `finding_id` do registro independente da vulnerabilidade, o `finding_node_id` do nó de exploração e o resumo da vinculação.

- `get_finding_traffic(finding_id)` usa o **ID do registro independente da vulnerabilidade** e retorna a lista ordenada e a `version`; passando `binding_id`, `side=request|response`, `offset` e `length` é possível ler por partes, com no máximo 8192 bytes por parte.
- O `finding_id` de `update_finding_report` **continua usando o ID do nó de exploração**. O novo `evidence_version` recebe a versão efetivamente lida; se as evidências mudarem durante a geração, a gravação com a versão antiga é rejeitada e é preciso ler e gerar de novo.
- Quando uma chamada de relatório antiga não envia a versão, não se afirma cobrir as evidências de tráfego existentes. Após mudança de vínculo, descrição, finalidade ou ordem, o relatório existente é sinalizado como pendente de atualização.

Com a vinculação automática ativada, `add_hint` / `add_task_hint` permitem salvar `traffic_refs` em cada dica individual ou em cada elemento de `hints` em lote. Quando o Planner reporta em nome de outro, pode passar `evidence_hint_id` para escolher explicitamente as referências da dica correspondente desta tarefa; não é possível referenciar dicas herdadas. O sistema não adivinha vínculos por domínio, horário ou histórico de navegação. Se o envio falhar, nenhuma vulnerabilidade parcial é gerada nem o relatório é disparado antecipadamente.

Para uma vulnerabilidade já existente que ficou sem vínculo, use `bind_finding_traffic(finding_id, traffic_refs)` para vincular depois, sem precisar registrar de novo. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` retornam `finding_id` e `finding_node_id` explícitos; o `id` antigo mantém a semântica de nó de exploração.

Na inicialização, apenas são adicionadas propriedades opcionais ao schema das ferramentas antigas; a vinculação padrão original das ferramentas de tráfego é estendida ao Agent de relatório, e a ferramenta de vinculação posterior é entregue por padrão ao Agent de relatório. Listas de vinculação personalizadas, prompts, descrições e estado de habilitação são preservados. A orientação é adicionada de uma só vez após a montagem final das ferramentas: o papel que reporta cuida de repassar as evidências existentes, e o Agent de relatório cuida de conferir, vincular e escrever o relatório. Quando a conversa da plataforma não tem contexto de tarefa, deve repassar ao Agent da tarefa por meio de dica estruturada, sem reportar diretamente. Antes de considerar a tarefa concluída, é preciso repassar as evidências existentes; sem pacote, não é obrigatório esperar. Um `report_finding` que falhou não dispara o Agent de relatório.

## API

Caminho base: `/api/exploration/findings/{finding_id}/traffic`, usando o ID independente da vulnerabilidade. Mantém a autenticação; `context_task` valida a visibilidade da tarefa e a herança somente leitura.

| Método / caminho relativo | Requisição / retorno |
| --- | --- |
| `GET` | Resumo ordenado, versão das evidências, versão adotada pelo relatório |
| `POST` | `{"traffic_refs":[...]}` anexa em lote completo |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"descrição"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, deve ser a lista completa |
| `GET /{binding_id}` | Metadados do snapshot e prévia limitada do corpo |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1` baixa os bytes originais completos |

Conflitos de versão/conjunto de ordenação e escrita durante o arquivamento retornam `409`; escrita em item herdado, `403`; vínculo inexistente ou que não pertence à vulnerabilidade, `404`; falhas de leitura/validação de tráfego/anexo retornam erro explícito.

## Armazenamento e migração

Migração idempotente do PostgreSQL na inicialização: adiciona `traffic_evidence_snapshots`, `finding_traffic_bindings` e `findings.evidence_version` / `report_evidence_version` (padrão 0). Não se completam vínculos adivinhando a partir de texto histórico.

O snapshot guarda o ID do tráfego original, o horário de coleta, URL, método, status, cabeçalhos de requisição/resposta, o tamanho do corpo e o SHA-256. O corpo é armazenado por hash em `<data>/evidence/blobs/<dois primeiros caracteres>/<hash>.bin`, independente do `data/traffic` que pode ser limpo, e várias vulnerabilidades podem compartilhar snapshot/corpo. O snapshot não oferece interface de atualização de conteúdo, e se a validação não bater, a leitura e a exportação falham.

O corpo completo é lido sob o bloqueio de escrita do tráfego original, incluindo blobs de corpos grandes e registros de diretórios antigos. Primeiro o arquivo é persistido e validado; depois uma única transação do PostgreSQL grava nó de exploração, relação de intenção, vulnerabilidade, snapshot e vínculo; só após o commit o planejador é notificado. Uma falha pode deixar arquivos sem referência, mas não produz registros de negócio parciais.

O advisory lock `7337741004` do PostgreSQL coordena os arquivos de evidência e as referências SQL; o bloqueio de linha da tarefa impede alterar evidências depois que o arquivamento entrou na fila. A restauração mantém o bloqueio de evidências da instalação do corpo até o commit dos metadados. Excluir a vulnerabilidade remove os vínculos em cascata.

O limpador roda a cada hora e recupera apenas conteúdo sem referência e que não esteja em operação em andamento, com atraso mínimo de 24 horas. A limpeza normal de tráfego não toca o diretório de evidências. Ao fazer backup dos dados quentes, faça backup ao mesmo tempo do PostgreSQL e de `data/evidence`.

## Exportação e arquivamento

O Markdown contém a lista ordenada de evidências e a versão; o JSON contém os metadados; o CSV ganha a quantidade e os IDs de vínculo. O `md-zip` mantém o Markdown da vulnerabilidade e fornece:

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

O Markdown referencia as mensagens por links relativos. Antes de enviar o download, são concluídos a cópia dos anexos, a validação de hash, a compressão, a sincronização em disco e a leitura/validação do CRC de todas as entradas do ZIP; ausência/corrupção faz o download inteiro falhar. Os anexos completos preservam os bytes binários originais.

O arquivamento v3 coleta snapshots e corpos pela relação de vínculo da vulnerabilidade, sem depender do tráfego original nem do domínio. Os dados quentes só são limpos depois que o pacote é validado; evidências compartilhadas continuam retidas. A restauração valida primeiro o corpo instalado e depois restaura metadados e vínculos em transação, com suporte a nova tentativa em caso de falha. v1/v2 continuam restauráveis, e os novos campos ausentes são preenchidos explicitamente com 0.

## Validação e limites

Cada pacote de teste usa um banco de teste PostgreSQL independente e recém-criado, indicado por `ARTEX_PG_DSN`, para evitar que resíduos de tarefas/modelos de fixtures disparem execução em segundo plano. Execute o teste completo dos pacotes relacionados e confirme que nenhum foi pulado por falta de configuração:

```sh
# Antes de rodar cada pacote, defina ARTEX_PG_DSN para o banco de teste independente correspondente; falha de configuração explícita deve gerar erro.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

A validação do frontend inclui `npx tsc --noEmit`, verificação Biome dos arquivos afetados, build Webpack e exportação estática com `NEXT_EXPORT=1`. Use um diretório de cache independente para não sobrescrever o servidor de desenvolvimento em execução.

A aceitação ponta a ponta local usa portas independentes, alvos HTTP / HTTPS com domínio controlados e um diretório de dados temporário, cobrindo as duas entradas de vinculação, seleção entre páginas, ordenação/descrição, mensagens de erro, herança somente leitura, download, e a exportação, arquivamento, recuperação do corpo quente, restauração e validação de hash após excluir o tráfego original.

A primeira versão adota um bloqueio global de coordenação de evidências; durante vinculação/exportação em lote grande ou download lento de anexos, outras operações de evidência podem ficar esperando. Sem registro gravado ou corpo completo, não é possível fabricar evidências. Este recurso não altera o interruptor de captura nem trata o problema de certificado ao acessar HTTPS diretamente por IP.
